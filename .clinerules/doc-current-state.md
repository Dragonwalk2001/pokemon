# 规则：文档只记录现状，不记录历史【强制】

适用于本项目**所有文档**——check_list、status / progress、TODO、设计文档、协议文档等一切以文字承载状态的文件，除非该文档自身有特殊说明。

## 核心原则

文档是给后来人看的**现状快照**，不是修复流水账。只回答「现在是什么样、为什么这么定」，不回答「我经历了哪些修复步骤」。修复过程属于 git 历史与 commit message，不属于文档。

## 不应该写：修复过程的痕迹

- 修前 / 修后的对比
- 删除线（~~...~~）
- "已修" / "已修复" / "refix" / "此前异常已消失" 这类过程标记
- refix、rerun 的日志路径

## 被取代的章节：直接删掉，不留存在过的痕迹

一节所描述的做法被新做法接管、已不属于当前链路，它就不再是现状，必须整节删除。

- 不留「已弃用」「已废弃，见 §X」「历史参考」这类墓碑标记，也不留空标题占位。
- 删之前把它承载的仍然有效的信息（结果数据、坑与解）迁进接管它的那一节，别连带丢掉。
- 删完重编号；重编号后，全文的 `§x.y` 引用必须一起改。

**边界**：被否决的对照实验不算被取代。「试过某变体、结果更差、故主管线不采用」这个结论本身就是当前主管线为何长这样的依据，要留，但只留结论和数字。

判据是：删掉这一节之后，读者会不会失去理解当前状态所必需的信息？会则留（说明它还是现状的一部分），不会则删。

## 已解决的坑怎么写

写法应是「状态：通过；坑：<根因>；解：<办法>」，而不是「之前 X 错了，已修成 Y」。坑与解只要仍是理解现状所必需的（防止后人再踩、解释当前设计为何如此），就保留，但以现状的口吻陈述。

## 写前自问

这句话在描述**当前是什么样**（保留），还是**我经历了哪些修复步骤**（删掉）？
